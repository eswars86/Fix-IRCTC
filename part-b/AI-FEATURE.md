# AI Feature Specification: Tatkal Success Predictor & Recommendation

## Problem It Solves
Addresses Problem 1 (Tatkal booking crashes and silent failures) from [PROBLEMS.md](../part-a/PROBLEMS.md). Specifically, this AI feature aims to reduce wasted Tatkal attempts by estimating per-request success probability and recommending alternative trains or strategies.

## Proposed Feature — User Perspective
When a user joins the Tatkal queue or attempts a Tatkal search, they see a small prediction card: "Estimated success: 28% — Try these alternatives" followed by 2 recommended trains or times and a short natural-language rationale ("Low success due to high recent attempts on this train; alternative B has open quota"). The card appears in the Tatkal queue view and on the search results page.

## Model or API Choice
- Availability predictor: XGBoost classifier trained on historical booking events (fast, explainable, and works well with structured features).
- Natural language guidance: OpenAI GPT-4 for generating concise, user-friendly rationale and alternatives based on structured model output.

Why: XGBoost provides a reliable, low-latency probability score for structured inputs; GPT-4 converts model signals into human-friendly text and helps craft alternative suggestions in fluent language.

## Training or Input Data
Data required:
- Historical booking logs: timestamp, train_id, class, quota, source/destination, result (success/fail), queue positions, response latencies.
- Live inventory API: current available seats by train/class (Railway API).
- Surge indicators: request-per-second metrics around Tatkal windows.
- Optional user history: user's past booking success rates (only if user consents).

Data location and availability:
- Railway inventory comes from live Railway APIs (requires integration).
- Historical booking logs are part of IRCTC backend (need access and anonymization for training).
- If historical data is not immediately available, start with a heuristics-based model and collect data for 2–4 weeks to train XGBoost.

## How Output Is Shown to the User
UI component: `TatkalPredictionCard` embedded inside the Tatkal queue card or results row.

Example:
Estimated success: 28% (low confidence)
Recommended: Train 12345 (alternate quota) — "Higher availability at 10:10"
[Why this suggestion?]  (opens brief explanation generated by GPT-4)

Confidence display: show probability and a confidence band (High / Medium / Low) based on model calibration and data freshness.

## Confidence Threshold and Fallback
- Show prediction when model confidence >= 0.6 (calibrated probability). If confidence < 0.6, hide the percentage and show only non-probabilistic guidance (e.g., "Demand is high; consider alternates").
- If the availability predictor service is down or latency exceeds 500ms, fall back to simple heuristic rules (recent seat consumption rate, alternative trains) and display a "heuristic" badge.

## Success Metrics
- Reduction in Tatkal attempts per successful booking (fewer wasted attempts) — target 15% reduction.
- Increase in successful alternative bookings suggested by the model — target +10%.
- User trust signals: % users who read the explanation and act on a recommendation (target > 5% click-through initially).

## Limitations and Risks
- Model bias: trained on historical data that may encode systemic biases (time zones, regional booking patterns). Monitor for fairness across routes and user segments.
- Over-reliance: users might rely on probability and skip legitimate attempts — make clear this is advisory.
- Data privacy: user history must be opt-in and handled per privacy rules.

## Implementation Notes
- Offline: Train XGBoost on historical logs; evaluate calibration and AUC.
- Online: run predictor as a lightweight microservice with cached features, and call GPT-4 only for generating the human explanation (keep prompts short and cache templated replies to reduce tokens).
- Cost considerations: minimize GPT-4 calls (use caching and templated generation); XGBoost inference is cheap and fast.
